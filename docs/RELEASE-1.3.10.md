# Letterpane 1.3.10 · план предварительного релиза

**Цель** — предсказуемое сохранение профиля и соблюдение пауз очереди после сбоя. Текущая база — 1.3.9. Версия 1.3.10 предложена для выпуска с исправлениями и прежними требованиями к Windows.

## Обязательные изменения

| Порядок | Задача | Критерий приёмки |
| --- | --- | --- |
| 1 | Согласовать запись правок из интерфейса и фоновой синхронизации. Снимок для фоновой записи должен содержать только подтверждённые правки. | Сохранение правки возвращает ошибку, одновременно завершается фоновая задача, затем профиль открывается заново. Правка отсутствует в новом сеансе, результат успешной фоновой записи сохранён, а интерфейс показывает ошибку и остановку очереди. Отдельный сценарий проверяет, что успешная правка переживает синхронизацию и перезапуск. |
| 2 | Сохранять перед запросом признак незавершённой попытки. После штатного завершения записывать фактические сроки пауз. После сбоя использовать консервативную паузу от момента восстановления, если фактическое время отправки неизвестно. | При задержке записи и аварийном выходе между отправкой и финальным сохранением раннего запроса нет ни глобально, ни для того же ящика. `Retry-After`, отмена задачи и остановка очереди при ошибке записи по-прежнему работают. Профиль 1.3.9 открывается с прежними настройками и сроками пауз. |

Тесты используют вымышленные профили, управляемое время и подставной почтовый сервис. Для второго исправления отдельно проверить границу между записью отметки и отправкой запроса. Если приложение завершилось на этой границе, более длинное ожидание при восстановлении допустимо.

## Эксперимент с размером portable

На предыдущем замере `node.exe` занял в ZIP 33,3 МиБ, а при отдельном сжатии Brotli — 27,2 МиБ. Собрать обычный и экспериментальный single EXE из одного коммита и сравнить размер, время от старта процесса до готового окна, а также целостность пакета. Для каждого варианта сделать по 10 первых запусков с пустым кэшем распаковки и 10 повторных запусков на той же машине. Записать медиану и диапазон. Для замеров использовать отдельный демонстрационный профиль.

Предлагаемый порог включения в 1.3.10 — экономия **от 5 МиБ на готовом EXE**, замедление первого запуска **не более 1 с по медиане**, повторного **не более 0,3 с**. Дополнительно должны пройти проверка целостности, восстановление после прерванной распаковки и запуск на чистых Windows 10/11. Если эксперимент не проходит пороги или требует крупного изменения загрузчика, выпустить исправления с обычной упаковкой. ZIP остаётся базовым вариантом поставки.

## Подготовка кандидата

1. После приёмки исправлений обновить версию и changelog. Запустить проверки исходников, `npm test` и `npm run test:ui`.
2. Собрать ZIP и portable EXE из одного коммита, выполнить `npm run verify:release` и `npm run smoke:release`. Приложить SHA256SUMS и ссылку на исходники и сценарии сборки того же коммита.
3. Проверить обе поставки на чистых Windows 10/11. На копии тестового профиля 1.3.9 проверить открытие после обновления, сохранение настроек, меток и пауз, повторный запуск и восстановление из копии. Записать версию ОС, хеш пакета и результат по [матрице QA](TESTING.md).
4. Перед публикацией подтвердить зелёный Windows CI на коммите кандидата и выполнить относящиеся к поставке пункты [релизного чеклиста](../RELEASE_CHECKLIST.md). Обозначить выпуск как preview. Для перевода в stable отдельно закрыть оставшиеся проверки из чеклиста, включая расширенную проверку Outlook.com и Microsoft 365 и проверку нативного интерфейса.

В следующем цикле рассмотреть кэширование сортировки аккаунтов и предупреждение об обрезанном письме. Прототип C# имеет смысл после замера готового portable EXE, если размер или холодный старт всё ещё ограничивают поставку. Импорт токенов и извлечение кодов вне объёма 1.3.10.
